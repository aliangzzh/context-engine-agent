# Code Review 与协作规范

## 分支与提交

- `master` 只接受通过 CI 的合并；功能开发走 `feat/xxx`、修复走 `fix/xxx` 分支。
- 提交信息用 `<type>(<scope>): <做了什么>`，一次提交只做一件事：
  - `feat(storage): 关系型历史存储 + 检索缓存`
  - `fix(frontend): 读取 used_tools 而非 usedTools`
  - `test(api): 补接口层与错误码测试`
- 一个提交里**不要混**"重构 + 功能 + 格式化"，否则 review 时看不出重点。

## PR 自查清单（提交前自己先过一遍）

**功能**
- [ ] 新接口有对应的 handler 测试 + 真 HTTP 测试（`tests/test_api.py`）
- [ ] 失败路径有断言：参数缺失/越界、未知资源、上游失败
- [ ] 前端改动在"接口没就绪"时能用 Mock 跑通（右上角开关）

**数据**
- [ ] 写多行的操作包在事务里，并有回滚测试
- [ ] 删除操作会同时清理索引/缓存（`kb_delete` 会清检索索引 + md5 指纹）
- [ ] 缓存有失效路径（`add_chunks` 后清空检索缓存）

**可观测**
- [ ] 关键路径有日志，且带 `request_id`
- [ ] 错误码是语义化的（40xxx/50xxx/502xx），不是裸 500
- [ ] 不把堆栈或密钥返回给调用方（`error_from_exception` 只给 msg）

**质量门**
- [ ] `python -m unittest discover -s tests` 全绿
- [ ] `ruff check backend` 无告警
- [ ] `npm run build`（含 `vue-tsc` 类型检查）通过

## Review 别人代码时先问的三个问题

1. **这行为什么存在？** 说不清楚的代码就是将来会腐烂的代码。
2. **删掉会怎样？** 删不掉的往往是"防御性代码"，那就把它变成测试。
3. **边界在哪？** 空输入、超长输入、并发、失败重试 —— 这些地方最容易出事。

> 团队 Review 文化里提到"会写清楚'为什么这样改'而不是只打回"，所以本仓库的
> 提交信息与文档都按这个标准写：讲取舍（为什么用 SQLite 而不是直接上 MySQL、
> 为什么自己写 multipart 而不是装依赖），而不是只写"改了啥"。
