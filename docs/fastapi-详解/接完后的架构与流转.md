# 接完 FastAPI 之后的架构与流转（好理解版）

> 前置：`fastapi-接入工作流程.md` 讲的是"怎么把 FastAPI 接进来"（阶段 0–10）。
> **这份讲的是"接进来之后，系统长什么样、一个请求怎么走、要改东西去哪一层"。**
>
> 所有数字都是本机实测（2026-09-20，`uvicorn app.main:app --port 8124`，
> `CHAT_BACKEND=fake` / `RETRIEVAL_BACKEND=bm25`），不是估算。

---

## 0. 一句话架构

> **HTTP 外壳（两个）→ 框架无关 handler → 服务门面 → 领域能力（Agent / 上下文引擎 / 检索 / 模型）→ 存储与缓存。**
>
> 一条铁律：**`context/`、`agents/`、`retrieval/`、`models/` 里不许出现 `from fastapi import`。**

这条铁律是整个架构的支点：内层不认识 HTTP 框架，所以同一份 `app/api.py`
能被两个完全不同的入口调用（FastAPI / stdlib），离线零依赖也能跑。

## 1. 分层图（左=调用方向，右=真实文件）

```
前端 Vue3 (#/对话 #/kb #/dashboard)
   │  fetch/SSE，只认相对路径 /api、/health
   ▼
【0】代理层    dev: vite proxy → 8000        prod: nginx → backend:8000
   │          frontend/vite.config.ts         frontend/nginx.conf
   ▼
【1】HTTP 外壳  二选一，互不依赖
   │     app/main.py (FastAPI)         │   server.py (stdlib)
   │     · request_id 中间件 + 访问日志  │   · do_GET/do_POST/do_DELETE 的 if/elif
   │     · 4 个 exception_handler       │   · safe_call 统一兜底
   │     · run_in_threadpool 卸阻塞     │   · ThreadingHTTPServer 天然多线程
   ▼
【2】路由判定 → api.py  handle_chat / handle_upload / ...  ← ★防腐层，唯一真相
   │            纯函数：(payload) -> (http_status, envelope)
   ▼
【3】服务门面 → services/chat_service.py  AppServices（懒加载单例）
   │            ★整个项目的线都插在 __init__ 那 10 行里
   ▼
【4】领域能力
   ├─ agents/orchestrator.py  Router→Retrieve/Tool→Writer + Middleware + Trace
   ├─ context/engine.py       build() 装配 slot → TokenBudget.allocate() 裁剪
   ├─ retrieval/retriever.py  BM25 / 向量 + 缓存
   └─ models/                 fake | qwen_api | local_ft（可插拔）
   ▼
【5】存储与缓存 → storage/db.py(SQLite/MySQL) + repo.py + cache.py(LRU/Redis)
```

**依赖只能从上往下，不能反向。** 换来一个很实用的性质：**改哪层，只测哪层往下。**

### 三个值得注意的地方

1. **第 ⑥ 步只在第一次请求发生** —— 之后 `_services` 不是 `None`，直接返回。所以"置办 7 个部件"整个过程只跑一次。
2. **第 ⑫ 步的四个参数里，三个是共享的** —— 只有 `_history(session_id)` 是这次会话专属。这就是"会话隔离 + 索引共享"落在代码上的样子。
3. **第 ㉝ 步是分水岭** —— 没超预算就直接返回（本次），超了才走裁剪分支。**"上下文满了怎么办"的答案全在 `engine.py:95-100` 那 6 行里。**

### 换意图时，图上哪一步变了

同一个 `orchestrator.py`，只有第 ⑰ 步的返回值不同：

| 用户说 | 判定位置（`router.py`） | 计划 | 图上多走的步骤 |
|---|---|---|---|
| "加绒牛仔怎么洗" | `:41` `_KB_KEYWORDS` | `["retrieve"]` | ⑲–㉓ 检索 |
| "北京今天天气" | `:37` `_WEATHER` | `["tool:get_weather"]` | `orchestrator.py:125-142` → `tools.py:81`（实测 1.96s） |

所以"加一种能力"的最小改动是 `router.py` + `tools.py`，**不必碰任何 HTTP 层代码**。

## 3. 场景 B：`POST /api/chat/stream`（SSE）

```
前端 EventSource/fetch-stream
  → main.py:139 chat_stream
  → run_in_threadpool(api.handle_chat_stream, ...)  ← ⚠️ 拿到的是【生成器对象】，函数体一行没执行
  → StreamingResponse(gen())  ← 真正迭代在事件循环线程上，线程池那层没生效
  → 事件序列：agent(路由) → agent(检索) → retrieved → token × N → done
```

- 事件协议是**契约**：`agent` / `retrieved` / `token` / `done` / `error`。
  **加字段可以，改事件名或删字段不行。**
- Nginx 必须 `proxy_buffering off`（`nginx.conf` 的 `/api/` location 里），
  后端响应头带 `X-Accel-Buffering: no`。少任何一个，前端都会"憋到最后一次性吐出来"。
- 流已经开了之后出错，只能把错误当成一个 `error` 事件发（`server.py` 的 `_send_sse` 有实现）。

## 6. 错误流转：三条路汇成一个形状（第四条漏了）

| 来源 | 捕获者 | 实测响应 |
|---|---|---|
| 业务主动抛 `AppError` | `main.py` `@app.exception_handler(AppError)` | 404 `{"code":40400,"msg":"知识库中没有来源：不存在","data":null}` |
| pydantic 校验失败 | `RequestValidationError` handler | 400 `{"code":40001,"msg":"参数校验失败","detail":[{"field":"body.message","msg":"Field required"}]}` |
| 未预期异常 | `Exception` handler | 500 `{"code":50000}`，**堆栈只进日志，不返回调用方** |
| **路径不存在** | ⚠️ **没人接** | 404 `{"detail":"Not Found"}` ← **形状不统一，实测复现** |

前三条收敛得很干净；第四条漏了，因为"路径不存在"抛的是 Starlette 的 `HTTPException`，
不归那三个 handler 管。**前端现在得写两套 404 解析 —— 这是接完之后最该先补的一刀。**

修法：

```python
from starlette.exceptions import HTTPException as StarletteHTTPException

@app.exception_handler(StarletteHTTPException)
async def http_exception_handler(request: Request, exc: StarletteHTTPException):
    code = ErrorCode.NOT_FOUND if exc.status_code == 404 else ErrorCode.BAD_REQUEST
    return JSONResponse(status_code=exc.status_code, content=fail(code, str(exc.detail)))
```

## 7. 记这五句就够

1. **`api.py` 是唯一真相**，`main.py` 和 `server.py` 都只是外壳 —— 加接口必须两个外壳都补，否则"离线模式"和"正式模式"会漂移。
2. **路由里不许有业务逻辑**。`/api/ping`、`/api/echo` 这种直接 `return {...}` 的写法一次犯两个错：绕过 `api.py` + 破坏统一响应体。
3. **`AppServices.__init__` 是总接线板**，`chat_service.py` 的 `AgentOrchestrator(...)` 决定一次对话拿到哪些能力。
4. **Context Engine 不是"把历史全灌进去"**，是"带优先级的 slot + 预算裁剪 + 滑窗摘要"，裁完还超就 `over_budget=True` 如实上报，不静默吞。
5. **排查问题永远先抓 `X-Request-ID`**，日志搜 `rid=`，同一个值横跨 HTTP 层、业务层、检索层。

## 7.5 服务面（`AppServices`）的接线图 —— 全项目唯一的总线

`app/services/` 整个包只有 5 行代码，实体是 `app/services/chat_service.py` 的 `AppServices`。
`api.py` 是"路由到业务的转换器"，`AppServices` 是"业务的总接线板"。

三个要点：

- **摘要器吃的是同一个模型实例**（`:41`）：切 `qwen_api` 时回答与摘要一起切；`fake` 不认摘要提示词，走规则模板降级。
- **配置只读常量，不在这里算**（`config.py:52/53/55`）：调参改 `.env`，服务面零改动。
- **工厂各自兜底**（`models/__init__.py:19` `_safe()`、`config.py:107` `effective_chat_backend()`）：没 key / 没 adapter 都不崩，降级成 `fake`。

### 7.5.2 向上接：服务面 → 防腐层 → HTTP 外壳

```
main.py:128  await run_in_threadpool(api.handle_chat, payload.model_dump())
                       ▼
api.py:49    def handle_chat(payload: dict) -> tuple[int, dict]:
api.py:51        return 200, ok(services().chat(req).model_dump())
                              └──────┬──────┘
api.py:31    def services() -> AppServices:      ← ★全项目唯一的单例入口
api.py:32        global _services
api.py:33        if _services is None:
api.py:34            _services = AppServices(seed_kb=True)
api.py:35        return _services
```

三条结构约束（靠结构保证，不靠纪律）：

1. **handler 里没有 `AppServices(...)`** —— 全走 `services()`，12 个 handler 共用一个实例。
2. **`main.py` / `server.py` 里没有 `services()`** —— 两个外壳只认 `api.handle_xxx`，这就是"双入口不漂移"的机制。
3. **懒加载** —— 进程起来不连库、不建索引，第一个请求才建。

代价：**全局单例难测**，靠 `api.py:38 reset_services()` 手动清（`tests/test_api.py:65`、`:71`）。
这正是 ADR D9 记的那笔账；换 `Depends()` 可以用依赖覆盖，但改动面大。

### 7.5.3 向下接：长命对象 vs 短命对象

持有的长命对象（进程级，只建一次）：

| 成员 | 类型 | 为什么必须长命 |
|---|---|---|
| `self.retriever` | `Retriever`（含 BM25 索引） | **内存索引是知识库"活"的那份**，重建就丢 |
| `self.model` | `ModelBackend` | 复用其内部连接/会话 |
| `self.store` / `kb_repo` / `feedback_repo` | SQL 连接 + `threading.RLock`（`repo.py:44`） | 连接跨线程不安全，实例必须共享 |
| `self.engine` | `ContextEngine` | 无状态但构造成本不低 |
| `self.metrics` | 环形缓冲 | 看板"最近 100 次请求"必须跨请求累积 |

按需组装的短命对象（`:46-57`）：

```python
chat_service.py:46  def _history(self, session_id) -> HistoryManager:        ← 每次请求新建
chat_service.py:47-51   HistoryManager(self.store, session_id,
                            max_turns=config.HISTORY_MAX_TURNS,
                            summary_tokens=config.HISTORY_SUMMARY_TOKENS)
chat_service.py:53  def _orchestrator(self, session_id) -> AgentOrchestrator: ← 每次请求新建
chat_service.py:54      AgentOrchestrator(self.retriever, self.model,        ← ★共享长命对象
                                           self._history(session_id), self.engine)
chat_service.py:56  def kb(self) -> KnowledgeBase:
chat_service.py:57      KnowledgeBase(self.retriever, self.kb_repo)          ← ★必须传共享实例
```

**这两处 `self.` 是整份代码最关键的两个字：**

- `AgentOrchestrator` 每次新建 → 每个 session 有自己的 `HistoryManager`（会话隔离）；
  但它握着的 retriever/model/engine 是共享的 → 不重复建索引。
- `KnowledgeBase.__init__`（`knowledge.py:84-86`）默认 `retriever or get_retriever()`。
  **不显式传 `self.retriever` 就会新建空索引** —— 上传成功、列表也看得到（DB 写了），
  但检索永远召回不到。这个坑在 `chat_service.py:57` 被堵住。

### 7.5.4 三种生命周期（记住这一张表）

| 层级 | 对象 | 创建时机 | 代码位置 |
|---|---|---|---|
| **进程级**（单例） | `AppServices` 及它持有的 retriever/model/store/repo/cache/metrics | 第一个请求 | `api.py:31-35`、`chat_service.py:32-42` |
| **请求级**（会话隔离） | `HistoryManager`、`AgentOrchestrator` | 每次对话请求 | `chat_service.py:47`、`:54`、`:73` |
| **调用级**（薄壳） | `KnowledgeBase`、`ChatReply`、`Health` | 每次对应调用 | `chat_service.py:57`、`:87` |

判断标准：**带 `session_id` → 必须每次新建；带连接/锁/大索引 → 必须共享。**

服务面向上的统一约定：**只吐 pydantic 模型或 dict，从不吐 HTTP 状态码**（状态码是 `api.py:51` 那个 `200` 的事）。

### 7.5.5 服务面的三个已知弱点

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| 1 | 全局单例难测 | `api.py:38` 靠 `reset_services()` 手动清 | 测试间互相污染知识库；并行测试打架 |
| 2 | `data/` 下有两个 SQLite 文件 | `chat_service.py:34` → `data/chat_history/history.db`（会话）；`repo.py:50` → `data/app.db`（kb_chunks/feedback） | 备份/迁移要一起带走 |
| 3 | **多进程下不成立** | 内存 BM25 索引 + 进程内 LRU 只活在单进程 | `uvicorn --workers 4` 会让 4 个进程各有各的索引 |

第 3 条是往后最先撞到的墙：**上多 worker 与"内存索引 + 进程内 LRU"互斥**。
要么单 worker，要么把索引外置（`config.py:61` 的 FAISS 持久化目录已留口子）。

## 7.6 orchestrator 解剖 —— 一个"项目经理"和他的一本手册

`app/agents/orchestrator.py`（212 行）是整个项目里最值得讲、也最容易被追问的文件。
**一句话**：它不干活，它安排谁在什么时候干什么活。判断靠路由员，干活靠资料员/工具箱/配菜员/模型。

### 7.6.1 目的（它自己写在 `:3-10`）

> 一个**小而自足的多 Agent 框架**：节点（Router、Retrieve、Tool、Writer）在**共享状态机**上协作，
> 外面套一层**生命周期中间件**，每个概念与 LangGraph 一一对应（节点/条件边/State/checkpointer）。

| 目的 | 靠什么实现 |
|---|---|
| 把"一次问答"拆成几个专职节点协作 | `for step in steps` 循环 + `state` 托盘 |
| 手写实现，**离线零依赖能跑** | 不 import langchain / langgraph |
| 结构与 LangGraph 1:1，随时可迁 | `Middleware` ↔ 钩子、`Trace` ↔ checkpointer、`state` ↔ StateGraph |

**关键设计**：它**不生成最终回答**。节点只负责"准备材料"，出文字是 `:173` / `:190` 调模型那一步。

### 7.6.2 代码结构：212 行分 5 块

```
┌─ 块 1  文件头注释（:1-11）             这是什么、为什么这么写、怎么映射 LangGraph
├─ 块 2  imports（:12-25）               把下游全部引进来
├─ 块 3  class Middleware（:29-42）      生命周期钩子（4 个空方法）
├─ 块 4  class RunResult（:46-56）       一次运行的结果（9 个字段）
└─ 块 5  class AgentOrchestrator（:60-212）  ★主体，152 行
        ├─ 常量 _SYSTEM（:61-64）         系统提示词
        ├─ __init__（:66-78）             接住 4 件家当 + 可选中间件
        ├─ _route_steps（:80-82）         探知识库 + 问路由
        ├─ plan（:84-89）                 对外：给前端看计划（不检索、不调模型）
        ├─ _describe_step（:91-99）       @staticmethod 计划步骤的文字说明
        ├─ _missing_args_hint（:101-108） @staticmethod 抽不到参数的追问话术
        ├─ prepare（:110-168）            ★核心：跑节点 + 装上下文
        ├─ generate（:170-179）           非流式出口
        └─ stream_events（:181-212）      流式出口
```

两处组织上的讲究：

- **`_describe_step` / `_missing_args_hint` 是 `@staticmethod`** —— 它们不碰 `self`（纯文本映射），标成静态方法表明"我不用任何状态"。
- **`plan()` 是唯一"空跑"的入口** —— 只调 `_route_steps` + `_describe_step`，**不检索、不调模型**，所以 `/api/chat/plan` 能秒回。

| 它不做 | 谁做 |

| 知道 HTTP 是什么 | 完全不关心 |

## 8. 要改东西时，去哪一层

| 你想做的事 | 改哪层（从内往外） |
|---|---|
| 加一个工具（如"汇率换算"） | `agents/tools.py` 注册 + `extract_args` 抽参规则；**不动** `api.py`/`main.py` |

| 调上下文预算/摘要轮数 | `config.py`（`CONTEXT_TOKEN_BUDGET` / `HISTORY_MAX_TURNS`），零代码改动 |

| 改响应体或错误码 | 只动 `errors.py` / `schemas.py`，**两个外壳同时受益** |
