# Agent 效果评测（评测集 → 策略优化 → 回归验证）

> 对应 JD 职责第 4 条：「参与 Agent 路由、RAG 检索及 Prompt 策略的效果优化，**建设评测集与回归验证，持续提升 Agent 准确率**」。
> 本文是这套评测的设计、口径与**真实跑出来的数字**；所有数字都能用一条命令复现。

```bash
cd backend
python -m eval.run                    # 开发集 30 题（CI 回归门用的就是它）
python -m eval.run --verbose           # 连通过的用例也打印实际信号
python -m eval.run --check             # 与 baseline.json 对比，回退则 exit 1
python -m eval.run --dataset dataset_holdout.json    # 留出集 #1（14 题）
python -m eval.run --dataset dataset_holdout2.json   # 留出集 #2（10 题）
python -m eval.run --category guard --verbose        # 只看兜底/拒答这一类
```

---

## 一、为什么这么设计

| 设计决定 | 原因 |
|---|---|
| **自带语料**（`eval/corpus/` 10 篇），不复用 `backend/data/kb/` | 线上/演示库里随时会多出上传文档（现在就有 13 块），分数会跟着飘。评测语料独立后，同一个 commit 在任何机器上跑出的分都一样 |
| 语料里塞 **4 篇干扰文档** | 只有 3 篇真文档时 hit@3 恒等于 100%，指标没有区分度。10 篇里 6 篇能答、4 篇是"话题相邻但不含答案"（物流/积分/安装/常见问题），top-3 才有意义 |
| 天气工具换成**确定性桩** | 真实 Open-Meteo 一抖动，同一份代码分数就变。评测要考"Agent 决策得对不对"，不是"外网通不通" |
| 评分器**去掉答案里的问题回显**再判 | fake 模型会把用户原话抄进答案（`（问题：…）`），否则 `forbid` 会命中"用户自己问的话"，把评分器的锅算到模型头上 |
| 分**开发集 / 留出集** | 阈值是在开发集上标定的；留出集是标定**之后**另写的，只用来暴露泛化缺口，不参与调参 |

## 二、题集：30 题五类（开发集）

| 类别 | 题数 | 在考什么 | 判定方式 |
|---|---|---|---|
| `routing` 意图路由 | 8 | 该走工具 / 检索 / 直接作答；**多意图**（"上海天气怎么样？另外帮我算一下 8*7"）是否都走到 | 路由计划集合相等 |
| `tool_args` 工具参数抽取 | 7 | function calling 的 `arguments` 那一步：城市名抽得对不对、算式抽得对不对 | 城市精确相等；算式**比对计算结果**（不比对写法，`(18+6)*3` 与 `18+6*3` 是两回事） |
| `retrieval` RAG 召回 | 7 | 期望来源是否进 top-3，并统计 hit@1 / MRR | 期望 `source` 在检索排序中的位次 |
| `answer_grounding` 答案事实覆盖 | 5 | 该事实是否真的进了最终答案（端到端） | 必备事实串全部出现在答案里 |
| `guard` 兜底与拒答 | 3 | 知识库不覆盖时**明说没有**而不是硬答；工具缺参数时**追问**而不是瞎调 | 出现禁用内容判失败；把无关片段当依据且未声明判失败；缺参未追问判失败 |

**离线口径必须说清楚**：跑的是 `fake` 模型（不联网、无 API key），它会回放检索到的片段，所以
`answer_grounding` 在离线下的语义是「**该事实是否被检索到并进入模型输入**」；换成真实模型后口径不变（事实覆盖），只是从"回放"变成"真的生成"。同理 `guard` 在离线下一部分检查天然通过（fake 不会编造），它的价值是**接真实模型后能用同一口径拦住幻觉**——这一点在设计时就写进了判定规则，而不是等接了模型再补。

## 三、消融：每一步优化带来的真实变化

> 数字来自 `backend/eval/reports/*.json`（工具桩 + BM25 + `fake` 模型，`top_k=3`，语料 10 篇 10 块）
> T07 的期望值在基线跑完后被更正过一次（42→72，(18+6)×3 本来就是 72）；两版下 T07 都是"基线失败、修复后通过"，**不影响任何一项指标**。

| 阶段 | 路由 | 工具参数 | hit@1 | hit@3 | MRR | 答案事实 | 兜底拒答 | **总通过率** |
|---|---|---|---|---|---|---|---|---|
| 基线 | 0.750 | 0.571 | 0.857 | 1.000 | 0.929 | 0.800 | 0.333 | **0.733** |
| +① 参数抽取 / 算式意图 | 0.750 | 0.857 | 0.857 | 1.000 | 0.929 | 0.800 | 0.333 | **0.800** |
| +② 多意图路由 | **0.250** | 1.000 | 0.857 | 1.000 | 0.929 | 0.800 | 0.333 | **0.700** |
| +③ 查询改写（领域同义词） | 0.250 | 1.000 | **1.000** | 1.000 | **1.000** | 1.000 | 0.333 | **0.733** |
| +④ 相关性门控 + 拒答兜底 | **1.000** | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | **1.000** | **1.000** |

每一步改了什么、为什么：

**① 参数抽取与算式意图**（`app/agents/tools.py`、`app/agents/router.py`）
- 全角括号/运算符归一化：`（18+6）乘以3` 旧版只抽出 `18+6`，算成 24（**错误答案**），修后 72；
- 中文运算符（`乘/加/除以`）现在能触发计算意图，但要求**夹在数字之间**——否则「加绒牛仔」的"加"会把洗护问题变成算数问题（这条专门加了单测）；
- 冷暖句式（`冷吗/冷不冷`）也能抽出城市：旧版把「成都今天冷吗」抽成城市 `成都冷`。

**② 多意图路由**（`app/agents/router.py`）
旧版命中第一个意图就 `return`，"天气 + 计算"这种一句两问会漏掉一个工具。改成收集全部工具意图。
**注意中间态：路由掉到 0.25** —— 这不是改错了，而是这一步把更深的问题顶到了台面上：`kb_relevant` 用的是
`bool(retriever.search(q, k=1))`，而字符级 BM25 对**任何**问句都能返回一条（共享一两个汉字就有分）。
旧代码里工具意图提前 `return` 把这个假信号挡住了；一改成"多意图收集"，假信号立刻让天气/算数问题全都多带一个 `retrieve`。
**这正说明：单点优化必须配评测集，否则你看到的是"改好了"，实际是把另一个缺陷露出了。**

**③ 查询改写**（`app/retrieval/retriever.py`）
`买回来不合适能退吗？` 的正确答案是售后政策，但 BM25 给颜色文档 1.0231、售后政策 1.0122——差 0.011，
因为字符级检索把"合适"当成了比"退"更强的证据。加一层**领域同义词扩展**（查询侧 `退 → 退/换`，中文
"退换/换货"是同一意图），售后政策得分反超 → hit@1 0.857 → **1.000**，答案事实覆盖 0.800 → 1.000。
（索引与查询共用字符级分词器，所以扩展只能加字不能加词——这是实现约束，写在代码注释里了。）

**④ 相关性门控 + 拒答兜底**（`app/context/rerank.py`、`app/agents/orchestrator.py`、`config.py`）
把"BM25 有分"换成可解释的 **内容词覆盖率**（先去掉口语停用词：的/了/吗/怎么/多少…），
要求「命中 ≥ 2 个内容词」且「覆盖率 ≥ `RELEVANCE_MIN_COVERAGE`（默认 0.35）」，同一判据用在三处：
1. **路由**：`kb_relevant` 用覆盖率判断 → 闲聊不再被带去检索（R05 通过，路由 1.000）；
2. **重排**：混合打分里的重合度也换成内容词覆盖率（停用词不再当证据）；
3. **上下文**：低于门槛的召回**不进上下文**，并在系统提示里追加"知识库没有相关内容，请如实告知" → 兜底 0.333 → **1.000**。

## 四、留出集：泛化到底怎么样

| 题集 | 结果 | 说明 |
|---|---|---|
| 留出集 #1（14 题，标定后写） | **0.857** | 抓到 2 个开发集没覆盖的缺口（下一行） |
| 同上，修完那 2 个缺口后 | 1.000 | **这套已被污染**（我按它的失败去改了代码），所以这个 100% 不能算泛化证据 |
| 留出集 #2（10 题，全部修复后另写） | **0.900** | 9/10；唯一失败是边界争议，见下 |

留出集 #1 抓到的两个真 bug（都已修 + 补了单测）：
1. `深圳明天会下雨吗？` 城市抽成 **`深圳会`** —— 兜底路径是"逐个删噪声词再拼回去"，"会"不在噪声表里就留下了脏字。
   改成**截到第一个时间/体感/疑问词之前**并排除"查/看/问/算"这类动宾残渣；
2. `重庆今天多少度？` 完全没走天气工具（旧触发词只有"温度/气温"，没有"多少度"）。

留出集 #2 的唯一失败（**已知边界，故意不修**）：
> `现在北京时间几点？` 被判成「时间工具 + 检索」混合意图（期望纯工具）。
> 根因：它与「常见问题.txt」共享"时/间"两字，覆盖率 0.4 刚过阈值 0.35。

不修的理由：这是**意图判定的边界争议**，不是缺陷——语料里确实有"工作时间 9:00-21:00"这类相邻内容，
"工具 + 检索"也算可辩护的行为。继续为它调阈值/加规则，就等于把留出集也变成开发集，
之后再没有干净的数字可看。**评测的纪律是承认边界，而不是把边界调没。**

**线上库实测的边界（冒烟测试发现）**：同一句 `你们支持花呗分期付款吗？`
在评测语料上会正确兜底（覆盖率 0.25 < 0.35），但在**本机现有知识库**上会保留 1 条并据此作答——
因为那个库里有 13 块内容，其中混着与业务无关的文档（如 FastAPI 笔记），字面覆盖率被噪声文档命中。
结论：**字面覆盖率门控的强度取决于语料质量**；生产环境应该先做来源/分类过滤或让用户选定知识库范围，
而不是只靠覆盖率。这条实测已记进本文件的已知边界，也是"评测语料必须与线上库隔离"的另一个理由。

## 五、阈值标定与过拟合声明

- `RELEVANCE_MIN_COVERAGE = 0.35` 是在**开发集**上标定的：需要判为相关的用例最低 0.43，最容易被误判为相关的只有 0.33。
- 这是**在评测集上调参**，存在过拟合风险，所以：①留出集不参与调参；②阈值做成环境变量（`RELEVANCE_MIN_COVERAGE`），
  **换语料/换模型后必须重新标定**；③开发集 100% 的定位是「回归门」（不许比已知最好状态更差），**不是**"线上准确率 100%"。
- `--strategy sentence|fixed` 已支持切分策略消融，但当前语料每篇都短于 `CHUNK_SIZE=500`，都是单块，
  两种策略跑出来没有区分度。**要拿到有意义的切分对比，语料里得放长文档**（后续工作，已列入待办）。

## 六、回归门怎么用

```bash
python -m eval.run --save-baseline    # 在"已知最好状态"上冻结指标
python -m eval.run --check            # 任何一项指标回退 → exit 1
```

`backend/tests/test_eval.py` 把这件事接进了单元测试（跑 `python -m unittest discover -s tests` 就会执行）：
- 题集完整性：用例 id 唯一、类别合法、每条都有 `note`、`retrieval` 的期望来源必须真实存在于语料；
- 回归门：开发集跑分不得低于 `eval/baseline.json`，且 `errors == 0`；
- 优化点定点单测：全角括号、中文运算符不误判、冷暖/下雨句式抽城市、缺参不瞎调、多意图、相关性门控正反例。
CI（`.github/workflows/ci.yml`）在跑完单元测试后执行 `--check`，并顺带打印两套留出集（留出集不作为门）。

## 七、要接真实模型 / 换语料，改哪里

| 想做什么 | 怎么改 |
|---|---|
| 换成通义千问等真实模型 | 配 `DASHSCOPE_API_KEY` 即可（评测台用的是项目统一的可插拔后端）；`answer_grounding` 会从"回放"变成真实生成，口径不变 |
| 加自己的语料 | 往 `eval/corpus/` 放 `.txt`；并同步更新 `dataset*.json` 里的 `expect.source`（完整性测试会替你检查） |
| 加题 | 往 `dataset.json` 追加一条（必须有 `id/category/question/expect/note`），跑 `--check` 看是否守住基线 |
| 换阈值 | 改 `RELEVANCE_MIN_COVERAGE` 后重跑开发集 + 两套留出集，重新 `--save-baseline` |
| 前端展示 | 报告落在 `eval/reports/*.json`（含每条用例的 expected/actual/失败原因），可直接喂给运行看板 |

## 八、这套评测能回答面试里的哪些问题

## 九、检索后端对比：BM25 vs 混合检索（改写查询探针集）

> 题集：`backend/eval/dataset_paraphrase.json`（10 题，口语化改写，尽量避开语料原词）
> 命令：`python -m eval.run --dataset dataset_paraphrase.json --retrieval bm25`
> 　　　`python -m eval.run --dataset dataset_paraphrase.json --retrieval hybrid`

| 指标 | BM25 | hybrid（BM25 + 向量，RRF 融合） |
|---|---|---|
| **retrieval_hit@1** | 0.200 | **0.300**（相对 +50%） |
| retrieval_hit@3 | 0.300 | 0.300 |
| **retrieval_mrr** | 0.250 | **0.300** |
| overall_pass_rate | 0.300 | 0.300 |

**两边的失败题完全相同**（P01–P06、P09 都失败）。也就是说：混合检索**没有救回任何一道"完全召不回"
的题**，它改善的是**排序** —— top-1 命中率和 MRR 上升，但 top-3 覆盖没变。

### 为什么差距不大：一个反直觉但重要的结论

在中文短文本上，**"字级 BM25 召不回"这件事本身很难发生**：BM25 按**单字**建索引，问句和文档
共享一两个汉字就有分，所以它的**召回面很宽，瓶颈是排序而不是召回**。

这正好解释了项目里为什么必须有"相关性门控"——旧版用 `bool(search(q, k=1))` 判断"知识库覆不覆盖
这个问题"，而字符级 BM25 对**任何**问句都能返回一条（见 §三 的 ②，那一版的中间态把路由打到 0.25）。
**同一件事，在路由和检索两个地方各暴露了一次。**

### 对"要不要上向量检索"的诚实结论

1. 当前语料规模（10 篇 / 10 块）与问法下，**BM25 的召回已经够用**，向量主要贡献的是**排序质量**；
2. 向量真正不可替代的场景是**跨表述 / 同义改写 / 多语言**。但本探针集里 **70% 的题两边都失败**，
   说明我把"避开原词"做得太狠，反而让问句变歧义了（例如"能不能拿热水泡？"既可能指洗护、也可能指材质）。
   **这是探针集的设计问题，不是检索方案的问题**——如实记录，不为了好看去调题；
3. 因此工程决策是：**默认 BM25（离线零依赖可跑），向量作为可选增强**，并且必须支持
   "索引不可用 / 与语料不一致时自动降级 BM25"——这正是 `retrieval/vector_index.py` 的三态
   （READY / STALE / UNAVAILABLE）要解决的问题。

**这个"负结果"本身就是可讲的**：评测的目的不是证明某个方案更好，而是**知道每个方案在什么条件下好**。
下一步如果要继续挖向量优势，应该重做探针集——目标不是"零字面重叠"，而是**同义词替换 + 保持问句自然**
（如「邮费谁出？」对「运费由买家承担」）。
